## ⚠️ 先看这条：商品状态的权威口径（本卡必须收口）

`backend/prisma/schema.prisma` 的 `Product.status` 注释是权威：**0 下架 / 1 在售 / 2 变更审核中**。后台 `admin-goods.service.ts#updateProductStatus` 也是 0 下架 / 1 上架；买家侧只认 `status: 1`（`product.service.ts:37`、`buyer.service.ts:367`）。

**但 `supplier-goods.service.ts` L10-14 的常量写错了**：

```ts
const ProductStatus = { PENDING: 0, ON_SALE: 1, OFF_SHELF: 2 }   // ❌ 与实际口径不符
```

后果（实害，不是我猜的）：**已下架的商品（status=0）在供应商列表里被显示成「待审核 / 已驳回」**，而 status=2 被显示成「已下架」—— 两个标签反了。大辉生产上刚下架的那个商品就是这个症状。

**要求**：把常量与映射按权威口径改对，且**不引入新的状态值**。显示判定顺序改成：

1. 该商品最新一条 **新品申请（type=1）** 若 `status=0` → 显示「待审核」；若 `status=2` → 显示「已驳回」（这两种商品不带上下架按钮）
2. 否则按 `product.status` 映射：`1` → 「在售」（若存在待审的变更申请 type=2 且 status=0 → 「变更审核中」）；`0` → 「已下架」；`2` → 「变更审核中」
3. 其它未覆盖的值 → 一律按「已下架」兜底（不许崩、不许白屏）

**必须交 6 组对照表实测**（种数据或改库后实跑，贴出「库内 status + 申请状态 → 前端标签」的逐行读数）。

## 一、接口（写死口径）

### 1. `PUT /supplier-goods/:productId/status`，body `{ status: 0 | 1 }`

- `0` = 下架，`1` = 重新上架；**免审即时**（不建 applications、不进审核队列）。
- **归属校验**：仅本人名下商品（`product_supplier_link` 查不到 → 404「该商品不存在或不属于本供应商」）。
- **值校验**：只收 `0/1`，其它值 → 业务错误「状态值不合法（0 下架 / 1 上架）」（照后台同款文案）。
- **拒绝"新品申请态"**：该商品最新 type=1 申请为 `status=0 或 2`（待审核/已驳回）时，不允许上下架 → 业务错误「待审核/已驳回的商品不支持上下架，请等审核结果或删除申请」。
- **留痕**：复用后台同款 action 名 `PRODUCT_ON_SHELF` / `PRODUCT_OFF_SHELF`（保持全库一致），`operatorId` = 供应商用户，`before/after` 带 `status`。

### 2. `DELETE /supplier-goods/apply/:applyId`（撤销/删除自建申请）

- **仅本人**（申请属于我的 supplier）且申请 `status ∈ {0 待审核, 2 已驳回}`；`status=1 已通过` → 业务错误「已通过的商品请用下架，不能删除申请」。
- **零引用才真删**：先查引用 —— ① `order_item` 有该 `productId` ② 该商品还有其它 `product_supplier_link` ③ 该商品还有其它 `product_application`。**任一存在就拒绝** → 业务错误「该商品已有历史订单/其它关联，不能删除，请改为下架」。
- 零引用 → **一个事务内**删除：本人的 `product_supplier_link` + 该 `product_application` + `product`（三张表要么都成、要么都不成；对齐卡B 定下的"多表写必须进事务"规矩）。
- **留痕**：`audit_log` 记 `SUPPLIER_APPLY_WITHDRAW`（`entity: 'product'`，`entityId` = 商品 id，`after` 里写清删了哪几张表 / 申请 id）。`audit_log` 无外键，商品删了留痕不受影响（已核实）。

## 二、前端（严格照原型屏 ④⑤⑥）

- 商品行按钮区：
  - 在售 / 变更审核中 → 「**下架**」
  - 已下架 → 「**重新上架**」，同时把「✏️编辑」「⚡改库存」**置灰**，点击给可读提示「商品已下架，请先重新上架再改价/改名」。
    ↳ 依据（不是拍脑袋）：后端 `quickStock` 已要求 `status === ON_SALE`（service L203），改价改名走审核也会撞 `PRODUCT_OFF_SHELF(3008)` —— 不置灰的话按钮点下去只会报错。
  - 待审核 / 已驳回（申请态）→ 「**删除**」
- 下架/上架/删除**都要二次确认**（用底部抽屉/居中弹窗，文案照原型：下架「下架后买家看不到这个菜；历史订单不受影响，随时可以重新上架」；删除「删除后无法恢复（这条申请会被撤掉）」）。
- **防连点**：操作进行中该行按钮禁用（贴出读数）。
- 成功后**就地更新该行**（不整页刷新）；删除成功该行**就地消失**。
- 失败给可读提示（把后端业务错误文案透出来），不许静默失败。

## 三、顺带修两处（我实测发现）

1. **超长封面地址回 5001**：`updateCover` 只做了白名单校验，没做长度校验；实测 301 字符的 `/uploads/aaa…png` → 白名单通过 → Prisma 撞 `VarChar(255)` → **http 200 + code 5001「服务异常」**。要求：加长度上限（≤255，与 `ApplyGoodsDto` 的 `@MaxLength(255)` 同口径）→ 返回业务错误「封面地址过长」。改完复测该用例，贴前后对比。
2. `ProductStatus` 常量的**名字与注释**一起改对（别再留着 `PENDING: 0` 这种误导后来人的写法；新品申请态由申请记录判定，不再靠商品 status 表达）。
