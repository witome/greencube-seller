## 零、背景与边界

- 上一卡做完了支付**写入侧**（抽象层 + 模拟回调 + 流水落库），但运营后台**看不到**这些流水。
- 本卡只加「**1 个只读接口 + 1 个后台页面**」：
  - **不改 schema**（`payment_record` 表结构不动）
  - **不动支付链路**（`modules/payment`、`order.pay()`、mock 回调一行不改）
  - 不影响小程序端（采购方/供应商/配送员三端全部不动）
- 金额口径**沿用已拍板**：线上支付金额 = **下单时刻应付额（`amountOrdered` + `deliveryFee`）**。

## 一、目标（做完长什么样）

运营后台新增「**支付流水**」菜单页：

1. **看什么**（列表列）：单号 `payNo` / 关联订单号 `orderId` / 渠道 `channel` / 金额 `amount` / 状态（待支付·成功·关闭）/ 创建时间 / 支付时间（未支付显示 `-`）
2. **能筛**：按状态筛选（全部 / 待支付 / 成功 / 关闭）
3. **能搜**：按订单号 或 单号搜索（一个输入框同时匹配两者）
4. **能翻页**：分页 + 总数
5. **纯只读**：页面上**不提供任何写操作按钮**（无退款、无关闭、无重试）

### 接口契约（建议）

```
GET /admin/payments?status=&keyword=&page=&pageSize=
  status   0 待支付 / 1 成功 / 2 关闭；不传 = 全部
  keyword  同时匹配 payNo（模糊）与 orderId（精确或模糊）
  page/pageSize  默认 1 / 20，pageSize 上限 100（对齐 audit.service 的 clamp 写法）

返回 { total, list: [{ id, payNo, orderId, channel, amount, status, statusText, createdAt, paidAt }] }
  amount  → 字符串两位小数（与既有接口 Decimal 序列化口径对齐）
  statusText → 待支付 / 成功 / 关闭
  paidAt  → 未支付返回 null，前端显示 '-'
```

## 三、需要拍板的岔路（选项 + 建议）

| # | 岔路 | 选项 | 我的建议 |
|---|---|---|---|
| ① | **本接口要不要写 `audit_log`**（金额相关） | A 不写 ／ B 每次查询留痕（操作人+筛选条件） | **A 不写**。理由：现有 `audit_log` 里**全部是状态变更类动作**（`REVIEW_BUYER` / `SPLIT` / `COD_PAY_PROOF` / `GENERATE_SETTLEMENT` / `SET_SUPPLY_PRIORITY` …），**没有任何一条只读查询写审计**；连 `/audit` 自身的查询接口也不留痕。只读接口写审计会让审计表被翻页噪音灌满、且与现状口径不一致。**若你更严，选 B 我照做**（需新增 action 常量，如 `VIEW_PAYMENT_LIST`） |
| ② | 列表要不要显示「**餐馆**」列 | A 显示 `shopName`（需 join `order.purchaser`）／ B 不显示，只给订单号 | **A 显示**。运营定位异常流水几乎必须有餐馆名，否则每次要跳去订单履约页反查。成本仅一次 join |
| ③ | **详情里要不要展示回调原文 `callbackPayload`** | A 列表不展示 + 详情抽屉只读展示 ／ B 后台完全不暴露 ／ C 本卡干脆不做详情，只做列表 | **A**（若你要最省，选 C 也能验收）。`callbackPayload` 是排查支付异常的唯一线索，本就是为留痕设计的；但**含 HMAC 签名等内部信息**，所以只给 ADMIN、只读、不在列表里明文铺开 |
| ④ | 接口归属 | A 新建 `admin-payment` 模块 ／ B 并入 `admin-finance` | **A**。命名与 `admin-order` / `admin-finance` / `admin-goods` 一致；且 finance 现有口径是「**结算 / 服务费 / 配送费**」，支付流水属「**收款**」，混在一起会让 finance 页职责变糊 |

## 四、验收标准（可判定）

1. **权限（铁律 3，硬门槛，必须逐角色实测）**
   - `admin` token → 200 且有数据
   - **`courier` token → 明确拒绝（2002 / 403），不得返回空列表**（配送员不碰钱）
   - **`supplier` token → 明确拒绝（2002 / 403）**
   - `business_agent` token → 拒绝（决策 5：业务员仅限采购方审核）
   - `purchaser` token → 拒绝
   - 无 token → 401
2. **字段完整**：每条含 `payNo` / `orderId` / `channel` / `amount` / `status` / `createdAt` / `paidAt`；金额为两位小数字符串
3. **金额口径正确**：任一 `status=1` 流水的 `amount` == 其订单的 `amountOrdered + deliveryFee`（抽查 ≥1 条，写明核对结果）
4. **筛选生效**：`status=1` 只返回成功；`status=0` 只返回待支付；不传 = 全部（三种各断言一次）
5. **搜索生效**：按 `payNo` 片段可命中；按 `orderId` 可命中
6. **分页生效**：返回的 `total` 与库内 count 一致；`pageSize` 上限 100 生效（传 200 实际返回 ≤100）
7. **纯只读**：本卡前后 `payment_record` 行数不因「查询接口」变化（查询不写库、不写流水）
8. **回归**：`cd backend && node 验收测试.js` → **基线 46/46 保持**，新增用例后为 **46+N / N，0 失败**（连跑两遍一致）
9. **编译**：`admin-web` build 通过；`frontend/` 无 diff（H5 与 mp-weixin 不受影响）
10. ⚠️ **预期现象，不是 bug**：列表里会出现 `status=0 待支付` 的**悬挂流水**（上一卡已明确欠账——全项目无订单超时关单机制）。验收时不得当缺陷处理。

## 六、依赖与风险

- **无外部依赖**：不需要商户号、不需要微信侧任何配置、不需要新账号。
- **风险面极小**：不动 schema、不动支付链路、不动金额与权限判定逻辑；新增物只有「1 个只读接口 + 1 个页面 + 1 个菜单项」。
- **数据依赖**：`payment_record` 表已有上一卡产生的真实流水，页面天然有数据可看；但**大辉已定「测试数据保留不清理」**，所以库里还混着验收/冒烟/调试造的采购方与流水——**本卡不清理**。若某环境表为空，需先跑一遍支付用例造数据（**属测试数据增量，需你许可**）。
- **细节对齐风险**：`amount` 的 Decimal 序列化（string vs number）要与既有接口口径一致；时间为 UTC ISO 存储，前端沿用后台既有 `fmtTime()` 本地化写法。
- **权限实现**：只需 `@Roles(Role.ADMIN)`（`RolesGuard` 已覆盖），但**必须在验收里显式测 4 个非 admin 角色**——上一卡的教训：写了不测 = 没写（当时 `mock/pay` 的权限 bug 就是这么溜过去的）。
- 环境提醒：迁移权限已由大辉修好（`lvlifang_app` 已具 DDL 权限），本卡虽不动 schema，如后续要迁移，`prisma migrate dev` 若报影子库错误就改 `migrate deploy`。
