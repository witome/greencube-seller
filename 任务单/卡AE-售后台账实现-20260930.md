## 一、一句话

订单走完就是走完；**售后是另一条线**：客户事后提申请 → 运营线下谈 → 运营点「处理完成」→ **客户和供应商都看到结果**。**全程不改订单金额与状态、不动任何钱的链路。**

## 二、五条红线（违反任意一条即算做错）

1. 🚫 **不改订单**：订单状态、`amountOrdered`、`amountFinal`、`order_item` 的任何数量字段都不许被售后改写。
2. 🚫 **不动钱**：不调微信退款、不改 `Settlement` 结算口径、不改客户账单、**不新增任何扣款/抵扣逻辑**。
3. 🚫 **不新加表、不新加字段**（供应商归属靠 join 推导）。唯一允许的 schema 改动是**改注释**（见 6j）。
4. ⚠️ **判定复用既有实现**：订单状态取值一律用 `common/constants/error-codes.ts` 的 `OrderStatus` 常量，**禁止写裸数字**；不得另写一份状态/金额判定。
5. ⚠️ **不许改现有断言的期望值**（基线 187/0 是权威口径；跑出问题先查自己，别改断言凑绿）。

## 四、要做的 7 件事

### 1) 后端 · 客户提交售后加三道门槛（`buyer.service.submitAftersale`）

现在只校验订单归属。要补：

- **订单状态**：`order.status ∈ {OrderStatus.DELIVERED(60), COMPLETED(70), SETTLED(90)}`，否则 `ORDER_STATUS_INVALID(3002)` + 人话（如「订单还没送达，送达后才能申请售后」）。
- **24 小时**：取该订单的 `deliveryTask.completedAt`；`now - completedAt > 24h` → 拒绝（人话：「已超过签收后 24 小时，请联系运营处理」）。取不到交付时间（没交付过）→ 也拒。
- **商品必选**：body 必须带 `orderItemId`，且该明细属于本订单，否则 `PARAM_ERROR`。
- **品质问题必须传照片**：`type=2` 时 `attachments` 不能为空（前端也拦一道，但后端必须真校验）。

### 2) 后端 · 落库口径

- `orderItemId` 用客户选的明细；`orderId` 从明细反查（不要信前端传的订单号）。
- `qtyDiff` = **客户填报的「涉及数量」**，上限 = 该明细的 `qtyReceived`（为空时用 `qtyAccepted`）。⚠️ 这是本卡的假定：不新增字段，就用 `qtyDiff` 承载客户填报数。
- `amountDiff` = `qtyDiff × orderItem.salePrice`（成交价快照）。**只作参考记录，不参与任何计算。**
- `status` 初始 0。

### 3) 后端 · 供应商归属（不落字段，查询时推导）

- 售后单 → `orderItemId` → `order_item.supplierId`（**核单时才写入，可能为 null**）。
- 为 null（未拆单）时：后台列表显示「**待分派**」，供应商端**不显示**该工单。
- 推导逻辑抽成**唯一一处**（如 `aftersale.service` 里的私有方法或共享 util），**三处调用都走它**：后台列表、客户侧回显、供应商端列表。

### 4) 后端 · 运营处理接口改造

- 动作语义改为「**处理完成**」（现有 `compensate` / `reject` / `close` 三个动作**保留可用**，别删；新口径下运营主要走「处理完成」= 现有 `compensate` 路径）。
- **`handleRemark` 必填**（空/纯空格 → 报错）。
- **`compensateAmount` / `compensateMethod` 选填** —— 现在代码里两个都传才放行（`admin-aftersale.service.ts` 约 96 行），**要放松成都不传也能完成**（金额为空时 `compensateAmount=null`，方式为空时按「仅致歉」处理或留 null，二选一但**要在代码注释里写明口径**）。
- 处理完成写 `handledBy` / `handledAt`，状态转 2（已解决）；审计沿用既有 AFTERSALE 审计，**payload 里不许出现多余 PII**。

### 5) 后端 · 去掉「确认收货自动建单」

- `order.service` 里确认收货的同一事务内自动建 `type=1`「少货」工单的那段**删掉**。
- ⚠️ 拒收本身照旧：`qtyReceived` / `rejectReason` **必须继续写**，只是不再建售后单。
- 删完自检：确认收货后 `aftersale_order` 应**零新增行**。

### 6) 供应商端新增只读接口 + 页面

- **新接口** `GET /supplier/aftersale`（`@Roles(SUPPLIER)`）：
  - 只返回**归属本供应商**的工单（经 `order_item.supplierId`）；
  - 字段：售后单号 / 订单号 / 商品名 / 类型 / 差异数量 / 状态 / 提交时间 / 客户照片 / 运营处理说明 + 处理时间 + 补偿；
  - 另给一个**待办数**（`status=0` 的条数）供首页红点用（可以复用同一接口返回 `pendingCount`，也可以单开一个，**你定，但要在交接里写清**）。
- **小程序**：新增 `subpkg-supplier/pages/aftersale.vue`（列表 + 详情，按原型 B2/B3）；首页 `home.vue` 加「售后」入口 + 红点数字（0 时不显示）；`pages.json` 注册。
- 页面上必须写明：**本页只读、不影响你的结算单**；**本期没有申诉/驳回入口**，只写「有异议请联系运营」。

### 7) 前端 · 客户侧改造 + 后台列改造

**客户侧（小程序）**
- `pages/buyer/order-detail.vue`：商品行加「申请售后」入口，**仅当订单状态 ∈ 60/70/90 时显示**；其它状态不显示（本卡主张：不显示，不做灰显）。
- `pages/buyer/aftersale.vue`（申请页）：加**选择商品（必选）**、**涉及数量**（上限 = 收货数量）、**品质问题必须传照片**（前端拦 + 后端真校验）；保留「不会自动退款 / 不影响订单金额与状态」的提示。
- `pages/buyer/aftersale-list.vue`：列表与卡片补**供应商**、**处理说明**；状态按**三档**文案（待处理 / 已解决 / 已关闭）。
- 现有「24 小时」两句文案**保留不动**（与新口径一致）。

**后台（admin-web）**
- `views/order/Aftersale.vue`：列表加**「供应商」列**（未拆单显示「待分派」）+ **供应商筛选**；处理对话框改为「**处理完成**」——处理说明必填、金额/方式选填，并加**二次确认**提示「处理后客户与供应商都会看到这段说明，工单转已解决不可再改」。

## 五、验收判据（每条都要可复现的证据，写进交接页）

1. 未送达（10/20/30/40/45/50）的单 → 提交售后**被拒**，且 `aftersale_order` **无新行**。
2. 已送达/已完成（60/70/90）→ **能提**。
3. 把 `delivery_task.completed_at` 改到 **25 小时前** → 被拒；**23 小时前** → 通过。（**造时间必须改库，不许只改前端**）
4. 不传 `orderItemId` / 传别单的明细 → 被拒。
5. `type=2` 不传照片 → 被拒。
6. 同一明细+同类型重复提 → 被拒；**不同类型可以**（同明细 type=1 后再提 type=2 应通过）。
7. 确认收货（含拒收量 > 0）→ **不再产生任何售后单**（`aftersale_order` 计数前后相等，`qtyReceived`/`rejectReason` 正常写入）。
8. 后台「处理完成」：说明为空 → 被拒；**不传金额与方式 → 能完成**，状态转 2。
9. 供应商端接口：只返回本供应商的工单；未拆单的工单**不出现**；`pendingCount` 与库内 `status=0` 条数一致。
10. **钱一分没动**：处理完成前后，`settlement` 与账单相关数字**逐字段相等**；订单 `status`/`amountOrdered`/`amountFinal`/`order_item` 数量**逐字段相等**。
11. 基线：`cd backend && npm run build && node 验收测试.js` → **187 通过 / 0 失败**；`npx tsc --noEmit` → **0 错**。
12. 新增自测脚本 `backend/scripts/aftersale-ledger-test.js`（**必须自己加载 `backend/.env`**，仓库既有脚本都是这么写的），覆盖上面 1~10；**自带清理**，跑完断言「自造数据残留 = 0」。
