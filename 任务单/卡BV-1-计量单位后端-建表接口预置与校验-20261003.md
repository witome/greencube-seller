## 一、要做什么

### 1. 新建「计量单位」表 + 迁移

表 `measure_unit`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BigInt PK 自增 | |
| `name` | VARCHAR(20) **唯一** | 单位名（斤 / 瓶 / 桶 …） |
| `sort` | Int，默认 0 | 越小越靠前，决定供应商端 chip 顺序 |
| `status` | TinyInt，默认 1 | 1 启用 / 0 停用 |
| `created_at` | DateTime 默认 now | |

**迁移里预置 18 条**（`sort` 按此顺序 1..18、`status=1`，用幂等写法如 `INSERT IGNORE`）：

`斤、公斤、袋、桶、箱、瓶、件、把、个、块、板、盒、包、罐、扎、提、捆、筐`

> ⚠️ 预置是**新表初始化**，**不动任何现有商品/申请数据**（大辉口径：现有商品不动）。

### 2. 接口

| 方法 | 路径 | 权限 | 行为 |
|---|---|---|---|
| GET | `/units` | 登录用户（供应商端 + 后台商品表单都用） | 只返回 `status=1`，按 `sort asc, id asc`；返回 `[{ id, name, sort }]` |
| GET | `/admin/units` | 运营（admin） | 返回**全部**（含停用），带 `status` 与 `statusText` |
| POST | `/admin/units` | 运营 | body `{ name, sort?, status? }`；**重名（含已停用的同名）→ 业务错 code 1001，文案 `该单位已存在，请换一个`**；`sort` 留空则追加到末尾 |
| PATCH | `/admin/units/:id` | 运营 | body `{ name?, sort?, status? }`；改名同样查重（排除自身）；启停靠 `status` |

- **不提供 DELETE**（口径：单位只用过就停用、不真删）。卡里明确写进代码注释，防后人加。
- 审计：新增/改名/启停各落 1 行 `audit_log`（沿用项目既有 `action` 命名风格，新增 action 时与既有写法保持一致，`entity='measure_unit'`, `entityId=单位id`）。

### 3. 供应商侧单位校验（核心）

改 `backend/src/modules/supplier-goods/supplier-goods.service.ts`：

- **删掉写死的兜底** `unit: dto.unit ?? '斤'`（现约 161 行）—— 供应商传什么存什么。
- 校验规则（**必须按此，别自己放宽也别收紧**）：

| 场景 | 规则 |
|---|---|
| `apply`（提交新品） | `unit` **必填**，且必须命中 `measure_unit` 里 **status=1** 的单位 |
| `editPendingApply`（编辑待审） | `unit` 可选；**传了就校验**；不传保留原值 |
| `:productId/change`（提交变更） | 同上（`changes.unit` 可选，传了才校验） |
| 任何写库路径 | 校验放行集合 = **启用中的单位 ∪ 该商品/该申请当前正在使用的那个单位** |

最后一条是关键：**老商品的单位如果已被停用，供应商编辑它时不改单位也必须能提交通过**（否则编辑老商品会被死锁）。这条要有测试用例。

- DTO：`unit` 保留 `@MaxLength(10)`，`apply` 的 `unit` 由「可选」改「必填」。
