## 二、逐条修法

### 修 1 · 「立即下单」重复下单（HIGH）

**文件**：`frontend/src/pages/buyer/goods.vue`

- 现状：`buyAll`（约 `:234`）**没有任何进行中标记**；同文件 `addAllToCart`（约 `:204`）已有 `submitting` 锁（`:190 const submitting = ref(false)`）。按钮在 `:73 <view class="cb-btn primary" @tap="buyAll">立即下单</view>`。
- 改法：**复用已有的那个 `submitting` ref（不许新建第二个）**——
  - `buyAll` 首行 `if (submitting.value) return`，随后 `submitting.value = true`，整个函数用 `try { … } finally { submitting.value = false }` 包住；
  - 按钮按同文件「加入草稿」既有那套禁用表达加进行中置灰（形如 `:class="['cb-btn primary', { dis: submitting }]"`，CSS 用文件里已有的禁用类，不许新造样式）。
- 判据：连点「立即下单」两次 → **只产生 1 张订单**（抓 `POST /order` 的请求条数 = 1；订单列表条数 +1）。

### 修 2 · 供应商端三处「提交/保存」无防连点（HIGH）

**文件**：`frontend/src/subpkg-supplier/pages/goods-manage.vue`

- 现状：全文件 grep `submitting|busy|saving` **零命中**。三个入口都直接 `await`：
  - `submit()`（约 `:838`，按钮 `:143`「提交申请」）→ `supplierApi.submitGoods()` → 后端每次新建 product+link+申请，**非幂等**；
  - `submitEdit()`（约 `:890`，按钮 `:261`「提交变更」）→ `applyChange()` / `quickPrice()`，非幂等；
  - `saveStock()`（约 `:874`，按钮 `:222`「保存」）→ `quickStock()` 免审即时生效。
- 改法：新增**一个** `const submitting = ref(false)`（三个入口共用即可，它们都是弹层里的一次性动作）；每个函数：首行 `if (submitting.value) return` → `submitting.value = true` → `try/finally` 复位；三个按钮加进行中置灰（用本文件已有的按钮禁用类，别新造）。`saveStock()` 顺带补 `try/catch`（失败时**弹层不关**、由 request 层 toast，别静默吞）。
- 判据：分别连点两次三个按钮 → 每个接口只被调用 1 次（`POST /supplier-goods/apply` / `POST /supplier-goods/:id/change` 或 `PUT /supplier-goods/:id/price` 的请求条数 = 1），列表里不出现重复申请。

### 修 3 · 连拍上架的资质图，运营审核端看不到（HIGH，含唯一后端改动）

**文件**：`frontend/src/subpkg-supplier/pages/batch-listing.vue` + `backend/src/modules/admin-goods/admin-goods.service.ts`

- 现状（复验过）：
  - 连拍 `buildBody`（约 `:464-478`）提交的是 `qualification: qualOf(d)`，**且完全不发 `images`**；
  - 单品链路 `goods-manage.vue:855` 提交的是 `images: formQual.value`（资质证明走 `images` 字段）；
  - 后端两条路都存（`supplier-goods.service.ts:171` 写 `product.images`、`:205-206` 写申请 payload 的 `images`/`qualification`）；
  - 但运营审核端只渲染 `images`：`admin-goods.service.ts:46-50` 只把 `images` 归一成数组返回，`admin-web/src/views/goods/GoodsAudit.vue:409` 也只取 `row.images`（全仓 grep `qualification` 在 admin-web **零使用**）。
  - ⇒ 连拍提交的商品，运营在「商品审核」页**只看到封面，看不到任何资质图**（`changePending()` 不返回 images/qualification，不用动）。
- 改法（两步都要做）：
  1. **前端统一字段名**：`batch-listing.vue` 的 `buildBody` 把 `qualification: qualOf(d)` 改成 `images: qualOf(d)`（口径与单品链路一致；**不要**两个字段一起发）。
  2. **后端兜底合并**（让已存在的老申请也能被看到）：`admin-goods.service.ts` 的 `pending()` 里，`images` 归一化时**把 `payload.qualification` 一并并入**（数组拼接、去重、过滤空值；`cover` 仍走 `cover` 字段不并入）。
- 判据：
  - 操作后台「商品审核」页，连拍提交的那条**能看到资质缩略图**（截图）+ 点开弹窗能看到大图；
  - 单品链路回归：用老入口提交一条带资质的新品，审核页展示与改动前**逐项一致**（截图）；
  - 库/接口证据：对一条连拍申请 curl `GET /admin/goods/pending`，`images` 数组非空。

### 修 4 · 配送员「确认交付」无防重复 + 无照片校验（HIGH）

**文件**：`frontend/src/subpkg-courier/pages/deliver.vue`

- 现状：`confirm()`（约 `:109`）无进行中标记，按钮（约 `:23`）只有 disabled 样式不拦点击；页面文案写着「📸 交付前拍照留痕」，但 `photos` 为空也能提交；`courierApi.deliverConfirm(taskId, { photos, remark })`。
- 改法：新增 `submitting` ref；`confirm()` 首行守卫 + `try/finally`；提交前**先校验** `if (!photos.value.length) { uni.showToast({ title: '请先拍摄交付照片', icon: 'none' }); return }`；按钮进行中置灰。
- **★ 明确不在本卡范围**：`signature`（电子签名）字段前端从未采集。**大辉 2026-10-04 已拍板：不做电子签名，交付留证只保留拍照**（照片必填见上）→ 本卡**不许加签名板**，报告里登记一句「按大辉拍板不做签名」即可（口径已写进 `任务单/项目交接页-踩坑与验收口径.md` 铁律第 11 条）。

### 修 5 · 购物车步进器连点少加/丢更新（HIGH）

**文件**：`frontend/src/pages/buyer/cart.vue`

- 现状 `changeQty`（约 `:297`）：
  ```js
  const qty = Number(it.qty) + delta      // it.qty 是服务端值，load() 没回来前是旧值
  await buyerApi.updateCart(it.cartItemId, qty)
  await load()
  ```
  两个快速点击读到同一个旧 `it.qty` → 目标值相同 → **连点 3 次「＋」最终只加 1**，用户观感是「点了没反应」。
- 改法（要的是**行为正确**，参考实现思路：本地目标值 + 每行串行补发）：
  - 维护每行**本地目标数量** `targetQty[cartItemId]`，渲染数量用 `targetQty[id] ?? it.qty`；点击时**立刻**改本地值（界面即时 +1）；
  - 同一行同一时刻**只允许一个 PUT 在飞**（每行 in-flight 标记）；在飞期间的点击只更新本地目标值、不发请求；
  - 在飞请求返回并 `load()` 之后，若本地目标值 ≠ 服务端最新值 → **补发一次** PUT，直到两者一致（设最多 3 次重试，失败则回滚本地值到服务端真值并提示）；
  - 数量减到 0 仍走既有 `remove(it)` 路径；`uni.$emit('cart-badge-refresh')` 保留；
  - **不许**在前端重算金额/合计（合计仍只用 `GET /cart` 的 `totalAmount`），`load()` 仍以服务端为唯一真源。
- 判据（真浏览器）：连点 3 次「＋」→ 界面立刻 +3 且不闪回；`GET /cart` 的该项数量 = 原值 + 3；同行的 PUT 请求**串行无并发**（抓包时间戳证明）。

### 修 6 · 订单列表加载失败会永久卡在「加载中」（MED）

**文件**：`frontend/src/pages/buyer/order-list.vue`

- 现状 `load()`（约 `:59`）：`loading.value = true` → `await getOrderList()` → `loading.value = false`，**没有 try/catch**。接口一失败 `loading` 永远为 true，空态/列表都不渲染，页面无任何反馈（这正是 `CODEBUDDY.md` 踩坑清单第 9 条）。
- 改法：按 `goods.vue` / `mine.vue` 既有写法加 `try/catch/finally`——`finally` 里必须复位 `loading`；失败时给**可见失败态 + 重试入口**；`onShow` 里补一次失败重试（`if (loadError && !loading) load()`）；`switchStatus` 连点加**请求序号**（自增 id，回来时不是最新一次就丢弃，别让旧响应覆盖新结果）。
- 判据：把后端停掉（或把接口地址临时指向不通端口）→ 页面显示失败态可重试，**不出现永久「加载中」**；快速连点两个状态筛选 → 最终列表与选中 chip 一致；恢复后端后点重试能加载出来。

### 修 7a · 切身份时轮询「护栏」失效（MED）

**文件**：`frontend/src/utils/new-order-alerter.js`

- 现状：`registerPoller` 只在 setup 时调用一次（约 `:97`），而 `stop()`（约 `:87`）里调了 `unregister()`。于是**首次 onHide 之后**它就不在全局登记表里了，`start()`（onShow）只重启定时器、**不重新登记** → 此后再切身份 / 退出登录，`stopAllPollers()` 停不掉它（旧页轮询会拿新 token 打旧角色接口；虽然 `isPermissionError` 会自停，但护栏本身已经漏了）。
- 改法：把登记与「定时器活着」绑定——**在 `start()` 里登记**（同 tag 覆盖），或让 `stop()` 不注销、只由 `onUnload` 注销。要求：**定时器在跑 ⇒ 登记表里一定有它**；`stopAllPollers()` 必须停得掉。
- 判据（H5 真浏览器，可自动化）：进入带 alerter 的页面（供应商首页）→ 切到「我的」再切回首页（制造一次 onHide/onShow）→ 触发切身份（Dev 角色浮窗或 `POST /auth/switch-role`）→ **切换后 35 秒内**统计旧角色接口 `GET /supplier-fulfill/stock-list` 的请求数：**修后 = 0**（修前 ≥1）。

### 修 7b · 切身份缓存清理收口（LOW，顺手）

**文件**：`frontend/src/store/user.js`

- 现状两处：① `BUSINESS_CACHE_KEYS = ['aiDraft', 'registeredRole', 'account_status']` —— **`account_status` 是拼错的 key**（全仓真实 key 是 `accountStatus`，见 `api/request.js` 与 `utils/logout.js`），所以这个键从来没被清掉；② `utils/batch-session.js` 的 `clearBatch()` 全仓无调用点，供应商切身份后「本批」角标会串到另一个档口。
- 改法：`'account_status'` → `'accountStatus'`；在 `clearBusinessCache()` 里调 `clearBatch()`（`import { clearBatch } from '@/utils/batch-session'`）。**不许**改 `switchRole` / `logout` 的既有跳转与订单流程。
- 判据：切身份后 `accountStatus` 与批次标记都不再是上一个身份的残留（代码级 + console 里 `uni.getStorageSync('accountStatus')` 为新身份值）。
