## 一、目标（一句话）

把现在只能「模拟支付」的支付链，换成**真实的微信支付 APIv3 小程序 JSAPI**：用户在小程序点「微信支付」→ 拉起微信支付面板 → 付款成功 → 微信回调到我们后端 → 订单自动从「待确认(10)」推进到「备货中(30)」。**同批补齐两处欠账：真退款、订单超时自动关单。**

## 二、生产已备好的凭证（**值只在服务器 `.env`，不许问、不许打印、不许写进任何文件**）

| 键 | 含义 |
|---|---|
| `WXPAY_MCHID` | 商户号 |
| `WXPAY_APIV3_KEY` | APIv3 密钥（32 位；**只有一个**，不要另设 APIv2 密钥）|
| `WXPAY_PUBLIC_KEY_ID` | 微信支付公钥 ID（应答/回调头 `Wechatpay-Serial` 会是它）|
| `WXPAY_CERT_PATH` / `WXPAY_KEY_PATH` | 商户API证书/私钥（`backend/certs/`，600）|
| `WXPAY_PUBLIC_KEY_PATH` | 微信支付公钥（**验签**微信的回调与应答）|
| `WXPAY_CERT_SERIAL` | 商户证书序列号（请求头 `serial_no`）|

**本机（你的开发机）不配真实凭证**（本轮不把生产密钥拷到本机）。本机用**自签测试证书 + 自选 32 位测试密钥**跑「本地假微信服务器」回路测试（见 §五），真链路由 Hermes 在生产验。

## 三、契约（写错这条就等于没做）

- **验签方式 = 微信支付公钥模式**（不是平台证书模式）。请求头 `Wechatpay-Serial: <公钥ID>`；按回调头里的 `Wechatpay-Serial` 选公钥验签。**不要**实现「下载平台证书」（该商户号下接口返回 `RESOURCE_NOT_EXISTS`）。
- **请求签名串**：`METHOD\nURL\nTIMESTAMP\nNONCE\nBODY\n`（URL 含 query；BODY 是原始 JSON 串；GET 无 body 时最后一行是空串）。
- **回调应答**：HTTP **200 + 空体**。⚠️ 本项目全局响应拦截器会把返回值包成 `{code,msg,data}`，这个路由**必须用 `@Res()` 直写**（见 `CODEBUDDY.md` 铁律 11）。
- **回调报文解密**：`AES-256-GCM`，key=APIv3 密钥，用 `resource.nonce` / `resource.associated_data` / `resource.ciphertext`。
- **回调地址**（不含 query）：`https://api.hsfresh.com/api/v1/payment/wechat/notify`（登记由 Hermes 做，你不用管）。
- **接口**：
  - 下单 `POST https://api.mch.weixin.qq.com/v3/pay/transactions/jsapi`
  - 退款 `POST https://api.mch.weixin.qq.com/v3/refund/domestic/refunds`
  - 查询 `GET /v3/pay/transactions/out-trade-no/{out_trade_no}?mchid=...`

## 四、要交付的代码（建议文件划分，可按你的判断微调，但职责要这样分）

1. `backend/src/modules/payment/wechat-pay.client.ts`
   v3 HTTP 客户端：加载证书/公钥、生成签名头、发请求、验签应答、AES-GCM 解密回调。**只此一份**签名/验签/解密实现。
2. `backend/src/modules/payment/wechat-pay.service.ts`（或并入 payment.service）
   `prepay(userId, orderId)`：
   - 校验订单属于该采购方、状态 10、`payMethod===0`（沿用现有 `order.service.pay()` 的校验口径）
   - **金额只用服务端库里的数**：`Math.round((amountOrdered + deliveryFee)*100)/100`，与现有 `payment_record.amount` 口径一致；**绝不接受前端传金额**
   - 关闭该单历史 `status=0` 流水、建新流水（`channel:'wechat'`，`payNo` 用**不可枚举随机串**作为 `out_trade_no`，≤32 字符），同一事务 + 写审计（沿用现有 `ORDER_PAY` 审计口径，note 写明「微信支付待回调」）
   - 调 jsapi 下单，返回给前端 `uni.requestPayment` 需要的参数：`timeStamp/nonceStr/package/signType('RSA')/paySign`（**paySign 用商户私钥对 `appId\ntimeStamp\nnonceStr\npackage\n` 签名**）
   `confirmPayment(notifyBody, headers)`：验签 → 解密 → **幂等**（流水已 `status=1` 直接返回成功）→ **金额核对**（与流水金额不一致则留痕拒绝）→ 复用现有 `completePaidOrder` 把订单 10→30（**不要另写一套推进逻辑**）→ 把原始回调写进 `payment_record.callbackPayload`。
   `refund(orderId, operatorId)`：调退款接口，`out_refund_no` **幂等**（可用 `R<payNo>`），金额以库为准，结果落库留痕 + 写审计。若订单已取消（流水 `status=3`）则直接把「已撤销/待退款」推进为「退款成功」。
3. `backend/src/modules/payment/wechat-pay.controller.ts`
   - `POST /payment/wechat/prepay`（采购方 token；DTO 只收 `orderId`）
   - `POST /payment/wechat/notify`（**无 token**，`@Res()` 直写 200 空体；异常也回 200 + 记录，避免微信重试风暴——但要在库/日志留痕）
   - `POST /payment/wechat/refund`（管理员 token）
4. `backend/src/modules/order/order-timeout.service.ts`
   `@Cron`（参照 `admin-dispatch/auto-dispatch-retry.service.ts` 写法，`ORDER_TIMEOUT_CRON` 可覆盖，默认每 10 分钟）扫出「`status=10` 且 `createdAt` 早于 `ORDER_PAY_TIMEOUT_MINUTES`（默认 30）前」的订单 → 订单置取消(91) + 把该单 `payment_record.status=0` 关成 `2` + 写审计。**只关微信待支付的单，别碰 COD**。
5. 前端
   - `frontend/src/api/modules.js`：加 `wechatPrepay(orderId)`、`requestRefund(orderId)`（若后台用）
   - `frontend/src/pages/buyer/order-detail.vue` 的 `pay()`：`payMethod===1` 时调 prepay → `uni.requestPayment({...})` → `success` 重新拉单；`fail` 且 `errMsg` 含 `cancel` 时提示「已取消支付，订单保持待确认」（**不要再弹模拟支付框、不要再调 mockPay**）；订单送达后那个「微信直接支付」按钮也换成 `uni.requestPayment`（先调 prepay 再拉起；COD 单走这条路=线上支付，保持与现有 COD 文案区分）
   - `mockPay` / `mock/pay` 相关调用**保留但不调用**（模拟通道 `WX_MOCK_PAY` 生产恒为 0）
6. 本地测试件
   - `backend/scripts/wxpay-fake-server.js`：自签证书对 + 自选 32 位密钥，模拟微信侧：返回 prepay_id、构造并加密回调（含「签名错」「金额不符」「重复回调」三个可切换模式）
   - `backend/scripts/wxpay-local-test.js`：跑完 §五 全部用例并打印 `通过 N / 失败 0`
   - 参照已有的 `backend/scripts/wx-fake-server.js` 的路子，别引新依赖（能不加包就不加；要用包先问）

## 五、本地验收（必须真跑，贴原始输出）

用 `wxpay-fake-server.js` + `wxpay-local-test.js` 跑，至少覆盖：

1. 正常回调（验签通过+解密成功）→ 订单 10→30、流水 `status=1`、`paidAt` 有值
2. 验签失败 → 拒绝、`callbackPayload` 留痕、订单**不动**
3. 同一回调重复投递两次 → 第二次幂等返回成功、订单/流水**不重复推进**（`audit_log` 不新增）
4. 金额不一致 → 拒绝 + 留痕 + 订单不动
5. 退款请求：假服务器断言收到的 `out_refund_no`、金额三者一致；重复退款请求幂等
6. 超时关单：把 `ORDER_PAY_TIMEOUT_MINUTES` 调成 1、造一条 10 状态单，等/触发一次 → 订单变 91、流水变 2、审计有记录
7. 回归：`cd backend && node 验收测试.js` 期望 **187 通过 / 0 失败**（前台或走管道跑，别重定向到文件）

另：**本机起后端时用 3011 端口**（另起一份 `.env`），别占用 3001 —— 那台机上 3001 可能被别的会话占用，会互相踩。

## 六、红线（违反任一条都算没做完）

1. **`WX_MOCK_PAY` 保持 0**，本机也不许开；不许为了让「支付能点」而接回模拟通道。
2. **任何密钥/证书内容不许出现在**：代码、日志、提交信息、报告、对话。（报告里写「已配置」即可。）
3. **金额一律服务端取数**，前端传的金额一律丢弃。
4. 回调**必须幂等**；验签/解密失败**必须留痕**再拒绝。
5. 订单推进**必须复用**现有的 `completePaidOrder` / 拆单逻辑，不许另写第二套。
6. 不许碰生产服务器、不许改服务器 `.env`（真链路由 Hermes 生产验）。
7. 改动 `order.service.pay()` 的响应字段时**保持向后兼容**（`orderId/payMethod/payNo/amount/status` 一个不删）。
8. 取证**不要用 agent-browser**（会卡死）；允许 `playwright-cli`、curl、脚本取证。
9. `自测证据/` **不入库**；只 `git add` 具体源码与任务单文件。
10. 别改 `CODEBUDDY.md`（Hermes 维护）；有改进口径的建议写在报告里。
