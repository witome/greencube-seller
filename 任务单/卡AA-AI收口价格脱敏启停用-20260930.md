## 需求 1：AI 把「我们没有的菜」配成别的商品

语音识别本身正确。问题是大模型遇到清单上没有的菜名时会自作主张配近亲菜（例：客户要杏鲍菇，它配香菇）。采购需求登记/到货通知这条链**已经做好了**（unmatched → `POST /buyer/demand/report` → 客户可订阅到货通知），不要重做。

改动：**只改 `backend/src/modules/ai/parser/llm.parser.ts` 的两个 system prompt（单句版 + ops 多轮版都要改，改一样的口径）**：

1. 硬规则里新增一条（两版同样写）：
   - 「清单里没有的菜名，**哪怕与清单里某个菜是近亲、看起来像同一种东西，也绝对不许配**。例如：客户要杏鲍菇而清单只有香菇/金针菇 → 必须进 unmatched，不许配成香菇；客户要牛肉而清单只有猪肉 → 必须进 unmatched。判断标准只有一个：**客户说的名字与清单商品名称是否对得上**，不按「长得像、是一类东西」判断。」
2. 现有「原话放进 unmatched，不要猜成别的商品」那条保留，措辞加强。
3. 除提示词外**不改任何解析/合并逻辑**。

验收：
- 新增自测脚本（放 `backend/scripts/ai-unmatched-strict-test.js`，可用项目里假模型的既有做法）至少 4 条：「杏鲍菇2斤」「荷兰豆10斤」「牛肉3斤」「牛油果2个」→ 断言 items 为空、unmatched 含原话；再放 2 条正常用例（清单里真实存在的菜名）断言正常命中。
- **生产真 Key 探针**：脚本写完后由 Hermes 在生产跑（你只负责脚本，生产你不碰）。

## 需求 2：未注册 / 未审核通过的采购方看不到真实价格

口径（已定，不许放宽）：**只有 purchaser 档案存在且 `accountStatus=2` 的用户能看到真实价格**；未注册、待审核(1)、驳回(3/4)、运营停用(5) 一律价格不可见。

现状：微信静默登录后无 purchaser 档案的用户，token 里 `currentRole` 默认是 `purchaser`，所以能调商品接口浏览 —— 这是现有机制，保留。

后端（价格在服务端抹掉，不许只做前端遮挡）：

1. `product.controller.ts`：`list` / `detail` 用 `@CurrentUser('userId')` 取 userId 传进 service。
2. `product.service.ts`：`list` / `detail` 内部按 userId 查 `purchaser.findUnique({ where: { userId }, select: { accountStatus: true } })`；
   - 可见：`salePrice` 照常返回真实值，并返回 `priceVisible: true`；
   - 不可见：`salePrice: null`，`priceVisible: false`。
   - `priceVisible` 是**纯新增字段**，其它字段一个不动。
3. `buyer.controller.ts` / `buyer.service.ts` 的 `GET /buyer/home-content` 同样处理（首页「今日推荐」也带价格）：controller 取 userId 传入，recommendations 每行按同一口径给 `salePrice` + `priceVisible`。
4. 「是否可见」的判定如果三处写法重复，抽一个小私有函数即可（限各自 service 内，或放 `product` 相关共享位置），**不许新建大模块**。

前端：
5. `pages/buyer/goods.vue`、`pages/buyer/goods-detail.vue`、`pages/buyer/home.vue`（今日推荐区）三处：
   - `priceVisible` 为真：照常显示真实价格；
   - 为假：价格位置显示 `¥**`，下方一行小灰字「注册审核通过后可见价格」，点该行/价格区跳转到注册页（`/pages/buyer/register`）。
   - 三个页面写法保持一致；若有可抽的小片段就抽，但不许大改页面结构。
6. 购物车 `pages/buyer/cart.vue` **不用改**（加购接口已要求 accountStatus=2，能进购物车的必然可见价）。
7. 下单链路、AI 确认页的价格仍由后端从 product 表回填，**不受影响、不许改**。

## 需求 3：运营后台对采购方「启用 / 停用」

现状：`AccountStatus.SUSPENDED=5` 常量、状态文案「运营停用」（admin-user.service.ts 里已有）都预留了，就差接口和按钮。

后端：
1. 新增 `PUT /admin/buyers/:id/status`：`@Roles(Role.ADMIN, Role.BUSINESS_AGENT)`，body `{ status: 2 | 5 }`（用 class-validator 校验，其它值拒绝）。
   - 只允许在 2（启用）与 5（运营停用）之间切换；目标当前状态不是 2/5 时报业务错误（如「当前状态不可启用/停用」），不许影响待审核/驳回流程。
   - 写 `audit_log`：停用 action = `BUYER_SUSPEND`，启用 action = `BUYER_REACTIVATE`；before/after 记 accountStatus，写法对齐本文件里 REVIEW_BUYER 等既有审计。
   - **一个事务内**完成改状态 + 审计。
2. 业务员(BUSINESS_AGENT)可以操作（与其它采购方审核接口同口径）。
3. 停用后：购物车/下单接口本来就只放行 accountStatus=2，会自动拒绝 —— 核对拒绝时返回的是**人话业务提示**（如「账号已停用，请联系平台运营」），不是裸 500/5001；不是就补上。
4. **进行中（已下单、备货、配送中）的订单照常走完，停用只挡新单，不动老单。**

运营后台前端（`admin-web/src/views/buyers/BuyerList.vue`）：
5. 列表行操作区：状态=2 显示「停用」按钮，状态=5 显示「启用」按钮；点击弹 `ElMessageBox` 二次确认（停用文案要写明「停用后该采购方无法下新单，已有订单不受影响」）。
6. 状态筛选/标签：状态 5 显示「运营停用」tag（后端 statusText 已有，前端 tag 配色补上）。

小程序端（停用后的用户体验，不许漏）：
7. accountStatus=5 的采购方进入小程序时，跳到一个「账号已停用」提示页：文案「你的账号已被平台停用，如有疑问请联系平台客服」，**无申诉按钮、无其它操作入口**。
   - 新建 `pages/buyer/account-suspended.vue`（可参考 verify-rejected.vue 的布局风格但文案不同），pages.json 注册；
   - 采购方页面（home/mine 等，grep 出全部入口共用一份判定，不许只挡一个页面）onShow 发现 5 即 `reLaunch` 到该页。判定数据来源与现有 profile/审核状态接口保持一致。
