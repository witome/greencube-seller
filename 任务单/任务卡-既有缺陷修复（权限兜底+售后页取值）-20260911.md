## 一、背景与边界

### 缺陷 1：权限兜底放行（违反铁律 3）

`backend/src/common/guards/roles.guard.ts:43-45`：

```ts
const allowed =
  required.includes(currentRole) ||
  (currentRole === Role.BUSINESS_AGENT && required.includes(Role.ADMIN))   // ← 本行删除
```

这行兜底让 `currentRole === 'business_agent'` 的 token 通过**任何** `@Roles(Role.ADMIN)` 接口。
铁律 3 规定「**业务员仅限采购方审核**」，因此这是**越权**：业务员可读资金结算、可改商品、可派单、可看审计日志、可看支付流水。

### 缺陷 2：售后管理页取值错误

`admin-web/src/views/order/Aftersale.vue:195-196`：

```js
list.value = res.data.list      // ← 错
total.value = res.data.total    // ← 错
```

`admin-web/src/api/request.js` 的响应拦截器**已解包** `{ code, msg, data }` 信封，直接返回 `body.data`。
所以 `res` 已经是 `{ total, list }`，`res.data` 是 `undefined` → `list.value = undefined` → **表格恒为空**。
（对照：同类正常页 `Payments.vue:136` / `AuditLog.vue:101` / `BuyerList.vue:318` 都用 `data.list`。）

### 边界（硬约束）

- **只动两个地方**：`roles.guard.ts`（删 1 行）+ `Aftersale.vue`（改取值）。
- **不许顺手改别的页面的同类写法**：`Aftersale.vue` 之外若还有同类 `res.data.list` 的页面，**只报告、不修**。
- 不动 schema、不动支付链路、不动小程序端（`frontend/` 必须**零 diff**）。

### 10.2 ★ 交付过程中的关键发现：上一卡的"红用例"是假红

复跑基线确认 64/1 后，新增用例**全部变红**——诊断发现根因不在守卫：
`backend/.env` 里 `JWT_SECRET` **带引号**（`JWT_SECRET="xxx"`），验收脚本用 `/JWT_SECRET=(\S+)/`
提取时把**引号一起吞进密钥**，与 dotenv 剥引号后的真实密钥不匹配 → 业务员 token 签名无效 →
守卫抛 **2001（未登录）而非 2002**。

**结论**：上一卡那条"业务员被拒"失败用例，其失败信号（2001）**从未真正触达守卫的放行逻辑**——
漏洞本身是真的（代码层可证，本卡用探针 B 实证），但上一卡把它记成"该用例暴露 RolesGuard 漏洞"属**归因错误**，此处更正。
脚本已改为先剥引号再签名，此后该用例才真正具备检验守卫口径的能力。
