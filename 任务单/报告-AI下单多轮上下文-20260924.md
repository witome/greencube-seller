## 二、接口契约变化（**纯新增可选**，老前端照旧可用）

```
POST /api/ai/parse
请求（新增，可都不传）：{ text, draft?: [{productId,qty,unit,name}], draftDeliveryDate?, draftRemark? }
响应（新增，仅在带了 draft 时给）：{ ...原字段不变..., changes?: [...], needClarify?: "...", draftVersion?: "8位指纹" }
```

- **不传 `draft`** → 走老路径，响应**逐字节不变**（下面第 ⑨ 条有 diff 证据）。
- 原有字段 `items/total/remark/deliveryDateLabel/deliveryDate/matchedCount/hasUnmatched/rawText/parser/unmatched` 语义一律未改。
- `changes[]` 是「本次每条变化」，中文文案由服务端生成（前端直接显示，不在前端再拼一遍）。

## 六、遗留问题 / 已知限制（不藏）

1. **降级路径只认「菜名 + 数量」的语序**（规则版既有特性，本次未改）：没 Key/模型挂了时，
   「再加5斤土豆」的「5斤」在菜名**前面**，规则版取不到 → 按 1 斤算；「猪肉」这类口语别名
   （→ 五花肉）规则版也匹配不到 → 表现为「今天AI有点笨」，但**已加的商品一个不丢、不报错**。
   规则版**不认**「改成/不要了/都不要了/那个」这四类说法 → 全靠大模型；这是「不配 Key 也能跑」的既定取舍。
2. **`白菜` 关键词重叠（既有缺陷，未动）**：规则版里 `大白菜` 命中后，`白菜001` 的 `白菜` 关键词
   仍会二次命中（基线输出里可见 `大白菜 1斤 + 白菜001 1斤`）。属规则匹配精度的老问题，
   **本次只报告不修改**（怕动它影响既定行为）。要不要修请大辉定。
3. **确认页改动不回灌聊天草稿**：用户在确认页调了数量再返回聊天页，聊天页的草稿卡仍是原来的数。
   取舍原因：确认页只回写 items，`total/amount` 会失配，若在前端重算就等于「第二份合并口径」（违反铁律）。
   建议后续做「确认页回写时顺带回写 total 或走一次服务端校验」，本次不扩范围。
4. **`draftVersion` 是内容指纹**（FNV-1a 8 位十六进制），不是递增版本号 —— 只用于比对「两次响应是不是同一份草稿」。
5. 备注沿用口径：新句子没提备注就沿用草稿原值；规则版降级时若它自己抽到了备注片段，会用它的
   （规则版 extractRemark 的既有行为）。
