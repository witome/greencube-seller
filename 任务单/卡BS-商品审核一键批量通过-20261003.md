## 一、需求

商品审核页要能**一键批量通过**，而且是**按筛选结果**批量（例：筛选某个供应商 → 全选 → 一次通过）。

现状（已核对代码）：
- 「待审核新品」tab（`admin-web/src/views/goods/GoodsAudit.vue` 5-35 行）：一张表，逐行「通过」（弹窗可设加价比例，留空=按档位自动）/「驳回」。**无筛选、无勾选、无批量**。
- 「待审核变更」tab（37-65 行）：同样无筛选/无批量，且「通过」**点一下直接生效**（立即改在售价格，**连二次确认都没有**）。
- 后端只有逐条接口：`POST /admin/goods/pending/:applyId/review`、`POST /admin/goods/change/:changeId/review`（`backend/src/modules/admin-goods/`）。

## 三、详细要求

### A. 前端 `GoodsAudit.vue`

1. **筛选条**（两个 tab 各自一套，或抽成一个组件都行）：
   - 供应商下拉（复用 `userAdminApi.getSuppliers()`，`admin-web/src/api/modules.js:39`）
   - 分类下拉（复用后台已有的分类接口，与商品管理页同源）
   - 关键字（商品名/商品名可选）
   - 「重置」按钮
2. **筛选必须是前端过滤**：把现有 `pendingList` / `changeList` 拆成 `allXxx`（接口原样数据）+ `filteredXxx`（computed），`<el-table :data="filteredXxx">`。这样**表头全选天然只作用于当前筛选结果**（这是本卡的关键实现点，不许用"手写 id 累加"绕过）。
3. **勾选列**：`<el-table-column type="selection">` + `@selection-change` 记录选中行。
4. **批量通过按钮**：文案带条数（如「批量通过（已选 3 条）」），未选中时禁用。
5. **批量确认弹窗**（新品与变更各一个）：
   - 新品：显示「将通过 N 条 / 涉及 X 个供应商 / 供货价 ¥a–¥b」；加价比例输入框**默认留空**，提示「留空 = 按 供应商 > 分类 > 全局 自动计算（与单条通过同一套逻辑）；统一填写会把这批商品都固定为「单品」比例」；
   - 变更：显示「将通过 N 条 / 涉及 X 个供应商」+ 红字提示「**通过后立即改动在售价格，对采购方即时生效**」；
   - 二次确认措辞里写明：「通过后如需改价，去商品管理改，或让供应商提变更」。
6. **变更 tab 单条「通过」补二次确认**（`ElMessageBox.confirm`，写明立即改在售价格）—— 现在没有，本卡一起补。
7. **批量结果反馈**：成功 N 条 → `ElMessage.success`；有失败 → `ElMessageBox.alert` 列出「商品名 + 失败原因」，失败明细要可读（别只报数字）。
8. 前端也拦一道上限：**一次最多 50 条**，超过给提示「一次最多 50 条，请分批」。

### B. 后端

1. 新路由（`@Roles(Role.ADMIN)`，参数校验走 DTO）：
   - `POST /admin/goods/pending/batch-review` → body `{ applyIds: number[], markupRate?: number }`
   - `POST /admin/goods/change/batch-review` → body `{ changeIds: number[] }`
2. 服务实现：
   - **逐条调用现有 `reviewApply(applyId, operatorId, { approved: true, markupRate })` / `reviewChange(changeId, operatorId, { approved: true })`** —— 严禁复制内部逻辑（定价解析、备注写 link、审计都靠被复用方法现成的实现）；
   - 每条**独立 try/catch**，一条失败不中断整批（不做整批大事务）；
   - 入参数组去重；`applyIds/changeIds` 长度 1~50，越界抛 `PARAM_ERROR`；
   - 返回：`{ total, approved, failed: [{ id, name?, reason }] }`；
   - 审计**不新增 action**：沿用被调方法已有的 `REVIEW_GOODS_APPLY` / `REVIEW_GOODS_CHANGE`（即批量通过 N 条 → 审计 N 行）。

## 五、验收标准（逐项可判定）

| # | 判据 |
|---|---|
| 1 | 新品 tab：选供应商 A 筛选 → 表头全选 → 只选中 A 的行（供应商 B 的行不被选中），点批量通过 → A 的行全部消失、B 的行仍在表里 |
| 2 | 留空批量通过 N 条后查库：每条 `product_application.status 0→1`；`product.markupRate` = 该商品档位解析值、`markupOverridden=0`、`salePrice = 供货价 × (1+比例)` 四舍五入 2 位 —— **与单条留空通过的结果逐字段一致** |
| 3 | 统一填比例（如 0.5）批量通过 2 条：查库两行 `markupOverridden=1`、`markupRate=0.5`、售价按 0.5 算 |
| 4 | 失败不中断：把 1 条已处理的 id 混进 10 条里 → 返回 `approved=9, failed=1`（原因「该申请已处理」），那 1 条状态不变，其余 9 条正常上架 |
| 5 | 审计：批量通过 N 条 → `audit_log` 新增 N 条 `REVIEW_GOODS_APPLY`（或 CHANGE），operator 正确 |
| 6 | 变更 tab：批量通过 2 条变更 → 对应 `product.salePrice` 按变更值更新（查库前后对照）；单条「通过」现在会弹二次确认，点取消不生效 |
| 7 | 上限：选 51 条（或直接打接口传 51 个 id）→ 前端提示分批 / 后端抛 `PARAM_ERROR` |
| 8 | 构建：`cd admin-web && npm run build` 退出码 0；`cd backend && npm run build` 退出码 0 |
