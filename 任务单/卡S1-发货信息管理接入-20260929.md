## 一、背景（真机验收卡在哪）

2026-09-29 真机点「微信支付」报「**由于小程序违规，支付功能暂时无法使用**」（errno 102 / 事件 `wxa_trade_controlled`）。

**技术侧已证明是通的**：后者 prepay 返回 **201** + 微信给了 `prepay_id`，`payment_record` 建出待支付流水，无 `SIGN_ERROR`。卡点在微信平台合规。

官方《实物电商类小程序运营规范》：提供实物商品在线销售及配送（**含同城配送**）的小程序**必须接入平台订单发货管理**，否则限制支付；且**用户付款后资金默认冻结，录入发货信息 + 确认收货后才结算**（快递 T+10、自提/同城配送 T+2 自动确认收货）。所以这个功能不做，钱也到不了账。

## 二、要交付的代码（三件事）

### 1. `backend/src/modules/wx/` 加发货信息管理能力

复用现有 `WxService.getAccessToken()`（已带缓存，凭证只读 `.env`，**不打印 AppSecret/token**）。

| 方法 | 接口 | 用途 |
|---|---|---|
| `isTradeManaged()` | `GET /wxa/sec/order/is_trade_managed` | 查该小程序是否已开通该服务（**联调第一步**，没开通就返回业务错提示去后台接入） |
| `uploadShippingInfo(...)` | `POST /wxa/sec/order/upload_shipping_info` | 录入发货信息 |
| `getOrderShipping(transactionId?/outTradeNo?)` | `GET /wxa/sec/order/get_order` | 查发货状态（对账/补偿/重试用） |
| `reportSpecialOrder(...)` | `POST /wxa/sec/order/opspecialorder` | 特殊发货报备（预售 / **测试订单**，避免测试单被判超时发货） |

**`upload_shipping_info` 关键参数（本项目是同城配送/自提，不用快递单号）**：
- `order_key`：`{ order_number_type: 1, mchid: <WXPAY_MCHID>, out_trade_no: <payment_record.payNo> }`
  用「商户号 + 我们自己的单号」形式，**不用微信支付单号**，省得存 `transaction_id`。
- `logistics_type`：**2**（同城配送）为主；若订单是用户自提则填 **4**（用户自提）。取值须与实际一致。
- `delivery_mode`：**1**（统一发货）。
- `shipping_list[]`：本场景**只需 `item_desc`**（必填，如「土豆 5斤、猪肉 3斤」汇总，≤120 字）；快递场景才要 `tracking_no`/`express_company`。
- `upload_time`：**RFC 3339** 格式，如 `2026-09-29T21:30:00.000+08:00`。
- `payer.openid`：买家 openid（`purchaser.user.wxOpenid`，卡R1 的 prepay 已在用同一取法）。
- ⚠️ **一笔支付单只有一次「重新发货」机会**，改发货模式/物流模式也算重新发货 → 调用前先判重，别重复调。
- 错误码处理：`10060002`（已完成发货）→ 视为幂等成功；`10060003`（已用掉重新发货机会）→ 记录并提示；`10060031`（openid 不匹配）→ 记录留痕。

### 2. 触发点：配送完成时自动录入

在**配送任务完成（订单置「已送达」）**那一步调用（复用现有送达逻辑的事务外副作用，**不阻塞主流程**：失败只记日志 + 落库待重试标志，不能让送达失败）。

- 需要拿到该订单的**已支付微信流水** `payNo`（`payment_record` 里 `channel='wechat'`、`status=1` 的最新一条）；未走微信支付的单（COD 现金/未支付）**不调用**。
- 落一个新表或复用字段记「发货信息已录入」状态，防重复调用（连同上面的「只有一次重新发货机会」）。
- 加一个**补偿入口**：管理端或定时任务，把「已支付但发货信息未录入/录入失败」的单捞出来重试（可参照 `order-timeout.service.ts` 的 `@Cron` 写法）。

### 3. 前端：订单详情页支持按 `payNo` 直达

**为什么**：微信后台「订单管理」要求填**订单详情页路径**，且约定用 `${商品订单号}` = 下单接口里的 `out_trade_no` = 我们的 **`payment_record.payNo`**（32 位随机串），**不是订单 id**。用户点发货/结算消息进来，带的是 `payNo`。

- `frontend/src/pages/buyer/order-detail.vue`：`onLoad` 除了 `opts.id`，再支持 **`opts.payNo`** —— 若只有 `payNo`，先调后端新增接口换成订单 id 再走原逻辑。
- `backend/src/modules/order/order.controller.ts` 加 `GET /order/by-pay-no/:payNo`（采购方 token，只返回**属于本人**的订单，口径同 `detail`）→ 找不到返回 404 业务错，不要泄露他人订单。

## 三、验收（缺一不可）

1. **单测/脚本**：本地起假微信服务（参照 `backend/scripts/wxpay-fake-server.js` 的做法）跑：
   - 未开通发货管理 → 业务错提示正确
   - 录入成功 → 请求体字段逐项断言（`order_number_type=1`、`logistics_type` 正确、`item_desc` 非空、`upload_time` 是 RFC 3339）
   - 重复录入 → 走幂等，不重复调微信
   - 录入失败 → 订单主流程不受影响，且能被补偿任务捞出来重试
   - `GET /order/by-pay-no/:payNo` 只能查到自己订单（换个 token → 404/403）
2. **全量回归**：`node 验收测试.js` 保持 **187 通过 / 0 失败**（当前基线）。
3. **生产真链路**：由 Hermes 在生产用真实 access_token 调 `is_trade_managed` + 对一笔**测试单**调 `opspecialorder` 报备（避开超时发货判定）。真机真付一笔由大辉做。

## 四、红线

- 密钥/token/AppSecret **不进任何文件、日志、报错、对话**；`access_token` 只走现有缓存，不打印。
- **不许为了让支付「能点」把 `WX_MOCK_PAY` 改回 1**。
- 发货信息**失败不能影响订单送达**（旁路副作用），但必须可追踪、可重试。
- `item_desc` 用真实商品汇总，不许写死占位文本。
