> 模式：**设计创意**（新任务页，不要塞进写代码的会话）。
> **交付物 = 单文件 HTML 原型 + 同名 PNG，不是代码。先不要碰 `backend/src`、`frontend/src`、`admin-web/src` 等任何源码目录。**
> 业务口径由大辉 2026-09-30 拍板（原话：「售后跟订单解耦、供应商要能看到、先不动钱的链路、线下处理、运营点完成并同步双方」）。

---

## 一、一句话说明白这张图要画什么

**订单走完就是走完；售后是另一条线。** 客户事后提申请 → 运营线下处理 → 运营点「处理完成」→ **客户和供应商都看到结果**。**全程不改订单的金额和状态、不动任何钱的链路。**

## 二、必须画在图上的三条硬边界（画成醒目的说明块，别只在正文里写）

- 🔴 **不影响订单**：售后**不改**订单状态与金额（客户侧要明确写出这一句，避免客户以为退款会自动到账）
- 🔴 **不自动退钱**：补偿是**线下**给的（微信转账/下次少收/补货），系统只记录
- 🟠 **前置条件**：只有**已送达/已完成**的订单能提售后；**送达后 48 小时内**；**必须选到具体商品**

## 三、屏清单（每屏都要画，并标「现状 → 改造后」）

### 【A 客户侧 · 小程序】

**A1 · 订单详情（售后入口）**
- 现状：订单详情有商品明细，没有售后入口
- 改造后：**仅当订单为「已送达/已完成」**时，商品行右侧出现「申请售后」入口；其它状态**不显示**（或灰显 + 提示"送达后可申请"）
- 对应实现：`frontend/src/pages/buyer/order-detail.vue`；门槛要写在后端 `POST /buyer/aftersale`

**A2 · 售后申请页**
- 现状：只有「选类型（少货/品质问题/错货/其他）+ 写原因 + 拍照」
- 改造后：**先选具体商品**（必选，从该订单明细里挑）→ 填**涉及数量** → 选类型 → 写原因 → 传照片（**品质问题必须传照片**，不传给出提示）→ 提交
- 页面上要写清：提交后由运营线下处理，**不会自动退款**
- 对应实现：`frontend/src/pages/buyer/aftersale.vue` → `POST /buyer/aftersale`（后端 `buyer.service.submitAftersale`）

**A3 · 我的售后（列表 + 详情）**
- 现状：能看状态/原因/补偿金额/运营备注/照片
- 改造后：补上 **「供应商」** 与 **「处理说明」**；状态四档要在图上标清（待处理 / 处理中 / 已解决 / 已关闭）并给出每档的客户侧文案
- 对应实现：`frontend/src/pages/buyer/aftersale-list.vue` → `GET /buyer/aftersale`

### 【B 供应商侧 · 小程序】

**B1 · 供应商首页（待办入口）**
- 现状：首页只有商品/报量/结算等入口，**没有售后，也没有消息/待办**
- 改造后：新增「**售后**」入口 + **红点待办数**（如「2 条待处理」）
- 对应实现：`frontend/src/subpkg-supplier/pages/home.vue`

**B2 · 供应商售后列表**
- 现状：无
- 改造后：只列**归属本档口**的售后：日期 / 订单号 / 商品名 / 差异数量 / 类型 / 状态 / 提交时间
- 对应实现：**新增接口** `GET /supplier/aftersale`（待实现）；页面新增 `frontend/src/subpkg-supplier/pages/aftersale.vue`

**B3 · 供应商售后详情**
- 现状：无
- 改造后：客户拍的照片（**可看**）、客户填写的原因与数量、运营的**处理说明**与结果、处理时间
- 页面上写明：**如有异议请联系运营**（本期**不做**申诉按钮）
- 对应实现：同上（待实现）

### 【C 运营后台 · PC】

**C1 · 售后列表**
- 现状：有列表（工单号/订单号/餐馆/类型/原因/差异数量/差异金额/处理结果/凭证/状态/提交时间/操作），**没有供应商列**
- 改造后：**加「供应商」列**（未拆单的显示「待分派」）+ **供应商筛选** + 状态筛选（待处理/处理中/已解决/已关闭）
- 对应实现：`admin-web/src/views/order/Aftersale.vue` → `GET /admin/aftersale`（后端 `admin-order/admin-aftersale.service.ts`）

**C2 · 「处理完成」表单（本期最关键的屏）**
- 现状：动作叫「同意补偿」，**必填**补偿金额 + 补偿方式（退款/补货/下次账单抵扣）
- 改造后：动作改为「**处理完成**」：
  - **处理说明（必填）** —— 写清线下怎么谈的（如"已微信退 12 元"、"下次补 5 斤"）
  - 补偿金额 / 补偿方式（退款·补货·下次账单抵扣·仅致歉）→ **选填**
  - 二次确认（提示：完成后**客户与供应商都会看到**这段说明）
- 对应实现：`POST /admin/aftersale/:id/handle`（动作枚举要改）

**C3 · 售后详情**
- 现状：有详情（含凭证照片）
- 改造后：补上供应商、客户提交的数量与原因、**处理时间线**（提交 → 处理完成）
- 对应实现：同上

## 四、这一版刻意没做的（图末尾也要列出这一段）

- 不接**退款**（不做部分退款、不调微信退款）
- 不**扣供应商结算**、不改**客户账单**
- 不做**供应商申诉/驳回**
- 不做**微信推送**（订阅消息模板要单独申请、供应商授权意愿低）
- 不做**责任方划分**（不区分供应商/配送/平台责任）
- 不做**补货单**（补货只在处理说明里写字）
- 不做**自动退差/自动赔付**
