## 一、选了哪个方案：**A（数据库层约束）**，并把写路径做成原子 upsert

**A 是唯一真正生效的修复，B 单独做不成。** 理由（不是偏好，是机制）：

1. **现在表上没有任何唯一键** —— 只有 `PRIMARY(id)`（已用 `SHOW INDEX` 核对）。
2. Prisma 的 `upsert` **必须有唯一选择器**（`where` 只能是 unique 字段/复合唯一）。`categoryId` 既不是 unique，又是可空，所以 `upsert({ where: { categoryId } })` 根本写不出来。
3. 退一步用原生 `INSERT ... ON DUPLICATE KEY UPDATE`：**没有唯一键时它会退化成普通 INSERT**，每次都新插一行 —— 等于没修。

所以：**A 是地基（库层保证「同分类至多一行」），B 的原子写法建立在 A 之上**。本卡两件都做了：

- **A**：新增生成列 `global_key = COALESCE(category_id, 0)` STORED + 唯一键。
- **写路径**：把「判存在 → create/update」两步压成**单条** `INSERT ... ON DUPLICATE KEY UPDATE`，让并发下的第二个请求**自动走更新语义**（这正是要求里更优的那条路：既不产生第二行，也不会抛错）。

### 为什么不是 `@@unique([categoryId])`（本卡的陷阱）

`category_id` 可空，而 **MySQL 的唯一索引不约束 NULL**（多行 NULL 被视为互不相同）。
`@@unique([categoryId])` 恰好挡不住最要紧的那条 —— **全局费率（`category_id IS NULL`）**。
只读核对（`SELECT (NULL = NULL), (NULL <=> NULL)`）：`plain_eq = null`、`nullsafe_eq = 1` ——
`=` 对 NULL 求值得 NULL、永不为真，所以唯一索引对 NULL 行不起作用。**那是「看起来对、其实没用」的修复，本卡明确排除。**

用 `COALESCE(category_id, 0)` 把「全局」归一成 `0`（`category.id` 自增从 1 起，0 不是合法分类 id，可安全作哨兵），
于是不论 `category_id` 是 NULL 还是具体值，同分类都只可能有一行。

**结论的边界说清楚**：
- **已实证**：同样的交错，现在第二个 INSERT 会被库拒绝（3.3 / 3.6）、并发写会被串行化（3.4）、并发保存只留一条（3.5）。
