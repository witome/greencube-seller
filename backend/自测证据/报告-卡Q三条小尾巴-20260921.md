### 1.2 口径（关键：不传时与改前完全一致）

```ts
// 都不传时，where 里不会出现 createdAt 键 → 查询条件与改前完全相同
const dayRe = /^\d{4}-\d{2}-\d{2}$/
const startDate = typeof query.startDate === 'string' && dayRe.test(query.startDate) ? query.startDate : ''
const endDate   = typeof query.endDate   === 'string' && dayRe.test(query.endDate)   ? query.endDate   : ''
if (startDate || endDate) {
  const range: any = {}
  if (startDate) range.gte = new Date(`${startDate}T00:00:00.000Z`)
  if (endDate)   range.lt  = new Date(new Date(`${endDate}T00:00:00.000Z`).getTime() + 86400000)
  where.createdAt = range
}
```

- **左闭右闭**：`>= startDate 00:00Z` 且 `< (endDate+1天) 00:00Z` —— 与改前客户端那套
  `day >= start && day <= end`（按 `createdAt` 的 UTC 日期切片比较）**语义逐字一致**，只是搬到了服务端。
- 非法格式（非 `YYYY-MM-DD`）一律**忽略 = 不筛**，避免脏参数 500。
- `status` 与日期可同时生效。

### 2.3 两个必须记住的坑（本卡实际踩到）

1. **⚠️ 大小写不敏感的比较会给出完全误导的结论。**
   首次执行后 `SELECT COUNT(*) WHERE action='courier_report'` 返回 **86**（看起来「一行都没改」），
   实际是因为库是 `utf8mb4_unicode_ci`：`=` 把 `COURIER_REPORT` 也匹配上了。
   **必须用 `CAST(action AS BINARY) = '...'`**（MySQL 8 里 `REGEXP BINARY` 报 3995，别用）。
   SQL 文件里所有比较已全部改成二进制，并在头部写明原因。
2. **⚠️ 必须先换代码、再改数据。**
   首跑时**旧后端进程还在跑**（写小写），UPDATE 之后它立刻又写进 1 行小写 ——
   于是需要二次执行才归零。SQL 文件的备份步骤已改成
   `CREATE TABLE IF NOT EXISTS ... LIKE` + `INSERT IGNORE`，**可重复执行且不会丢早先的备份**。

### 3.3 为什么判断「可以改」（而不是只报告）

- **幂等不受影响**：守卫在 `supplier-fulfill.service.ts` 的 `applyDeclareUpdate()` 里，是
  `tx.orderItem.updateMany({ where: { id, qtyAccepted: null, isAutoDeclared: 0 } })` **条件更新**
  —— 由数据库在写入那一刻判定，跟「读 link 用哪条连接」无关。本次**没碰**这段（原文已附在证据文件里）。
- **超时边界不受影响**：候选筛选（`it.qtyDeclared === it.qtyOrdered` 等）来自事务**外**那次
  `order.findMany`，本次未改；`autoQty = min(qtyOrdered, dailySupply)` 的计算输入列（`dailySupply`）本身没变，
  变的只是**读它的连接** → 从「事务外的另一条连接、读最新已提交」变成「事务内、读本事务快照」。
  两者只有在「同一时刻正好有人改了 `product_supplier_link.dailySupply`」时才会有差异，
  而那次写入本来就会在下一次兜底时被读到，不会累积错误。
- **净收益**：①读与随后的写一致（原来读在事务外、写在事务内，口径不统一）；
  ②**修掉一个真实隐患** —— 交互式事务里再向连接池借第二条连接，高并发下可能把池占满而互等。

## 五、本机环境踩到的坑（供后续卡片省时间）

1. **Bash 的 PATH 被 shim 弄坏**（`dirname: command not found` → 连带 `ls/head/node/mysql` 全找不到）。
   临时解法：命令开头显式 `export PATH="/c/Users/Administrator/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:/c/.../mingw64/bin:/c/Windows/System32:/c/Program Files/MySQL/MySQL Server 8.4/bin:/c/Users/Administrator/.workbuddy/binaries/node/versions/22.22.2-3"`。
2. **`npm run dev` 被沙箱拦**：它触发了 `wsl.exe`（在程序黑名单里）→
   启动 admin-web 要直接跑 `node node_modules/vite/bin/vite.js`。
3. **`mktemp -d` 不可用**：返回 MSYS 路径 `/tmp/...`，原生 node 读不到（会解析成 cwd 下的怪路径）→ 用固定 Windows 临时目录。
4. **`playwright-cli run-code` 的载荷里不能出现反斜杠**：会被 bash 转义破坏 → 整段 payload 语法错、**静默不执行**（表现是「没报错但也没结果」）。取路径改用 `u.split('/api/v1').pop()`。
5. **`git -C <仓库根> diff -- src/...` 的 pathspec 是相对仓库根**，不是相对子目录 → 写 `backend/src/...` 才有输出。
6. `admin-web` dev server 绑在 **`[::1]:5190`**（IPv6 localhost），用 `localhost:5190` 访问正常。
