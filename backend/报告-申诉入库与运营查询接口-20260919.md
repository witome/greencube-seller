## 一、加哪张表 / 哪些字段 / 为什么（动手前的一句话）

> 新增一张 **`appeal_record`（申诉记录，一条申诉一行）**，字段
> `purchaser_id`(FK→purchaser.id，权限归属) / `user_id`(提交账号) / `text`(正文) /
> `attachments`(JSON，URL 数组) / `reason_code` + `reject_reason`(提交时刻驳回原因快照) /
> `status`(0 待处理 / 1 已处理) / `created_at` / `handled_by` + `handled_at`(运营处理留痕)，
> 索引 `purchaser_id`、`(status, created_at)`；并给 `Purchaser` 加反向关系 `appealRecords AppealRecord[]`。
> **为什么**：决策 6 要求申诉正文 + 附件必须入库。原 `appeal()` 只做两件事（`appealCount30d>=1` 拦截、
> `accountStatus→PENDING` + 计数 +1），把 `dto.text` / `dto.attachments` **直接丢掉**并返回假 id `0`，
> 运营根本看不到申诉内容 —— 等于白交。

### 1.1 表结构（实际落库，`DESCRIBE appeal_record`）

## 六、踩坑与说明（避免下次再犯）

### 6.1 ⚠️ curl 的 argv 会破坏中文（本次实际踩到，已修正）

- **现象**：`curl -d '{"text":"中文"}'` 提交，落库变成乱码 `��Eȡ֤…`；而 `node fetch`（验收测试）写入的中文正常。
- **根因**：Git Bash 把命令行参数传给原生 `curl.exe` 时按系统码页转换，UTF-8 中文被破坏。
  **不是后端/DB 的问题**（`purchaser.shop_name` 里 node 写入的 `#24验收餐馆` 原样保存，已对比验证）。
- **修法**：所有带中文的 body 先落成 **UTF-8 文件**，再 `curl -d @<文件>`
  （文件路径要用 Windows 形式 + `MSYS_NO_PATHCONV=1`，否则 curl 找不到文件）。
- **连带处理**：早期版本脚本产生的 2 行乱码测试数据（`appeal_record id=1,2`）已清理（纯 DML、未改 schema），
  清理前内容已留在证据文件里。最终表中仅 `id=5,6` 两条正确数据。

### 6.2 另外两个本机坑（已写进脚本注释）

1. 环境变量 `http_proxy` / `https_proxy` 指向沙箱代理 → curl 打 localhost 报 `upstream connect failed`，
   必须加 `--noproxy '*'`。
2. `node` 读不了 MSYS 的 `/tmp/xxx` 路径，必须用 Windows 形式（脚本里统一用 `$TEMP`）。

### 6.3 已知观察项（本卡不做）

- `GET /admin/appeals` 目前**只读**，不提供「运营在后台勾选已处理」的写接口——
  处理入口仍走既有的 `POST /admin/buyers/:id/appeal-review`（受理即打留痕）。
  这是刻意的：决策 6 只要求「运营能看到」，不新增第二套处理流程。
- `appeal_record` 无「同一次驳回多次申诉」的历史约束校验（`appealCount30d` 仍是 30 天 1 次），
  与既有业务规则一致，未改。
